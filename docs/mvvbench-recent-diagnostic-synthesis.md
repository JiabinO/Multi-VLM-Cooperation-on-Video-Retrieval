# MVVBench 近期诊断实验整理

更新日期：2026-11-17  
用途：为下一阶段的多视角协作实验确定问题与验证顺序。本记录区分观察结果、暂时解释和待验证假设；案例级实验不外推为整体能力结论。

## 1. 研究问题如何收敛

最初的研究动机是：多视角 VLM 答错，究竟是单视角本身没有提取到关键信息，还是不同视角之间的对应与整合出了问题？随后把诊断拆成两个由浅入深的问题：

1. 不给 QA 问题时，模型能否从两张同场景图像中发现共同实体和空间线索？
2. 告知同场景、不同机位，或提供人工确认的共同实体后，模型能否稳定描述视角差异？

选择题答案位置偏差也需要单独控制，否则多视角 QA 的变化可能混入选项顺序影响。

## 2. 已完成的实验与观察

### 2.1 足球案例：从目标检测到跨视角关系

案例为 `iiith_soccer_016_4-q00488`，问题问“与球门内的球相似的球，相对男子在哪一侧”。人工查看确认球门内有一个白球，场上另有橙球；View 2、View 3 提供的视角信息不同。此前多视角回答错，而单视角结果不一致，因此进一步拆查模型是否看见目标、是否识别对应球，以及是否能从视角信息判断左右。

- **全画面与球门裁剪**：OpenRouter 上的 Nemotron 3.5 Super VL 在全画面中多次说球门为空；单独给球门裁剪后能看到白球。说明该案例至少有图像分辨率/局部细节可见性问题。
- **全画面加裁剪**：模型虽然能说出球门内是白球，却仍把画面中的橙球当作唯一场外候选，并回答无法确定。检测到目标不等于完成了目标对应和关系推理。
- **多视角证据输出**：有的回答仍称球门内无球；另有回答凭空提到黑白球。用户人工复核确认场景目标为白球和橙球，因此这些模型叙述不能作为事实证据。
- **关系单独检查**：提示模型不必重新识别颜色、只报告球相对人的位置后，单视角和跨视角输出仍出现左右不一致；跨视角调用还遇到截断、空回答和免费模型额度错误，部分结果无法用于比较。

**案例级结论**：至少需要区分局部目标可见性、跨视角实体匹配、坐标系/左右关系推理和调用完整性。裁剪改善了球门内白球的识别，却没有自动修复“哪一个球与之相似”以及“它在人哪一侧”的推理。模型自报置信度偏高或不一致，未做校准，不能据此认定答案可靠。这个案例推动了后续不提供 QA 问题的两图关系诊断。

### 2.2 104 题多视角诊断：背景信号

诊断覆盖 104 题（EgoExo 88、MMPTrack 16），共完成 662 条条件预测。总体结果中：

- 全输入条件准确率为 0.404。
- 每题事后挑选最佳单视角的 oracle 准确率为 0.538；全视角独有答对 3 题，最佳单视角独有答对 17 题。
- 全视角、每视角 2 帧的准确率为 0.442；每视角 4 帧为 0.404，配对差值约 +0.038。

这说明现有模型与提示下，增加视角或帧数没有稳定地转化为更好的回答。最佳单视角是看过答案后的 oracle，只作诊断上界，不能当作可部署策略。上述统计是当前模型和采样条件下的现象，不证明多视角信息本身无用。

### 2.3 选项顺序诊断：`64pm_industry_safety_4-q01281`

对 View 0 与 View 3 分别将四个选项做完 24 种排列，使用本地 Qwen3-VL-8B：

| 单视角 | 24 次中选择展示位置 A | 还原到原始选项标签的次数 | 正确率 |
|---|---:|---|---:|
| View 0 | 12/24（50%） | A=3，B=13，C=7，D=1 | 0.125 |
| View 3 | 9/24（37.5%） | A=3，B=10，C=10，D=1 | 0.125 |

“展示位置 A”高于无位置偏好时的 25% 参考值，是位置偏好的初步信号；但这些调用是同一模型、同一题的确定性重复排列，并非独立样本，且准确率低。因此暂不作统计显著或普遍偏好结论。后续报告应同时保留“显示位置”和“还原后的原始选项”，避免把位置效应与内容判断混为一谈。

### 2.4 两图空间关系诊断：同一道工业场景题

使用 `64pm_industry_safety_4-q01281` 的 `all_views_frames_2` 条件中 View 0、View 3 的第一帧；不提供题目和选项。三种提示各运行 A→B、B→A 一次，共 6 次：盲测、告知同场景不同机位、提供候选共同锚点。

**盲测**：两种输入顺序都提到三脚架、黄线、白色地砖和红柜等线索，判断画面来自同一实验室的相近区域。但模型把“同一组人员”“相同位置的柜子/椅子/工作台”等也列为共同实体，部分对应关系未经核验；机位描述仅为“角度略不同”或“取景略不同”。

**告知同场景后**：模型给出更具体的左右、上下方向，但交换输入顺序后没有可靠地反转方向。例如 A→B 说 B 在右下，反向输入时仍说相机向右、向下。提示虽然引出了具体说法，当前输出并不具备顺序一致性。

**提供候选锚点后**：模型围绕黑色三脚架、红橙色立杆和地面标记组织回答，但 A→B 与 B→A 的水平相对方向仍不一致。截图中三脚架与地面标记是有用的候选线索；“两张图里的三脚架一定是同一架”尚未得到独立核验，因此该条件应称为候选锚点提示，而非可靠真值条件。

**案例级结论**：模型似乎能识别“相近场景”并提出候选共同物；但从共同物到有明确参照系、可随输入交换而反转的空间关系，当前表现不稳定。模型自报的 high/medium 置信等级没有被校准，不能当作概率。由于提示没有强制逐图报告锚点位置，当前结果也无法区分“看错锚点位置”和“推断相机方向错误”。

## 3. 当前结论与边界

目前不应假设每个端点 VLM 都能准确、全面地提取本视角信息，也不应把 QA 错误一概归因于多视角融合。更合适的工作假设是：错误可能发生在至少三个环节：

1. **单图观察**：目标或细节是否被看见、识别正确。
2. **跨图对应**：不同图中的人物、物体或固定地标是否真是同一个。
3. **关系与答案推理**：对应物已正确后，位置变化是否被正确解释并用于回答。

目前的 104 题结果和工业场景案例支持把这些环节分开诊断，但还不能说明哪一环节是数据集总体的主要瓶颈，也不能证明加入显式视角关系就会提升 QA。

## 4. 建议的下一步

### 第一步：把空间关系任务改成可核验的两段输出

已按这个设计新增 `scripts/diagnose_anchor_displacement.py`：对同一对图像和候选锚点，分别记录 A、B 中的可见性与 3×3 画面位置，再描述从 A 到 B 的图像平面位移；交换图像顺序复跑，检查位置对应及位移方向是否反向。它不要求模型推断现实世界的相机方位。服务器运行尚待完成。

先用三脚架和黄色地面标记做候选锚点；将三脚架是否确为同一架作为待核验项。工作人员可辅助识别，但不作为固定空间点。红柜重复较多，避免仅凭颜色将它们认作同一个柜子。运行命令见 [两图空间关系诊断说明](mvvbench-pairwise-view-relation-diagnostic.md)。

### 第二步：用少量案例检验可重复性

先选 5–10 对图像，不追求全面人工复核。人工只记录：共同物是否确实相同、锚点位置大致是否读对、模型的位移描述在顺序交换后是否反向。对无法确定对应物的样本标成“不确定”，不强行打分。

### 第三步：再回到 QA 与系统设计

只有当模型能稳定报告锚点和画面位移后，才把这些结构化关系作为额外证据加入原 QA，比较答案是否改善。若位置读取本身就不稳定，系统应显式保留不确定性、请求另一端复核，或避免把未经确认的跨视角对应物当作事实。研究目标可从“假设各端可靠，再压缩传输”调整为“在端点观察有误差时，选择、对齐并校验值得传输的跨视角证据”。

## 5. 后续记录建议

每次新增实验只更新四项：样本与模型版本、实际输入图像/帧、控制变量、结果与局限。保留原始模型输出；人工判断单独记录，不覆盖模型预测。总体准确率、案例解释和待检验假设分开书写。
